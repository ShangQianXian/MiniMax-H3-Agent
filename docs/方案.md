# MiniMax H3 Agent 实施方案与实现记录

> 状态：**已实现并通过验收**。本文档同时是实施方案与实现记录，末尾附「实现与计划的差异」。
> 官方接口文档原件见 `docs/api/`（7 份）。

## 1. 目标与成功标准

**目标**：构建一个纯工作流引擎形态的 Agent WebUI —— 左侧栏管理「项目 / 节点库 / Skill」，中间无限画布 + 节点图，右侧节点参数检查器；节点直接调用 MiniMax H3 全系列接口，**不引入任何 LLM 编排**。

**成功标准与验收结果**：

| # | 标准 | 结果 |
| :- | :--- | :--- |
| 1 | 画布上串联「提示词 → 视频生成」并运行，能真实创建任务并看到状态流转 | ✅ 集成测试覆盖创建→queued→running→succeeded |
| 2 | 三种生成场景走通：t2va / i2va（首帧、尾帧、首尾帧）/ r2va | ✅ 场景自动判定 + 槽位解析测试 17 例 |
| 3 | Context-IR 增强提示词可回流到下游生成节点 | ✅ 保留 rawText 快照，下游拿到增强文本 |
| 4 | 768P 产物可一键发起 2K 再生成 | ✅ 按源视频 / 按任务 ID 双模式 |
| 5 | 任务中心支持筛选、取消、删除、产物转存 | ✅ 状态机与接口限制严格对齐 |
| 6 | 每个节点与全图显示预估费用 | ✅ 与官方价格表逐档对齐（单测断言） |
| 7 | 项目与画布持久化，刷新/重启不丢 | ✅ node:sqlite + 900ms 防抖自动保存 + 运行时恢复 |
| 8 | 非法参数在发送前被拦截并给出中文错误 | ✅ 前端即时校验 + 服务端权威校验双重把关 |

## 2. 技术选型（已落地）

| 层 | 选型 | 理由 |
| :--- | :--- | :--- |
| 前端 | React 19 + Vite 7 + TypeScript 5.9 | 与参考界面一致的现代 SPA 栈 |
| 画布 | `@xyflow/react` 12 | 开箱即用的节点 / 端口 / 缩放 / 连线，避免自研画布 |
| 状态 | zustand 5 | 全局图状态 + 手写撤销重做（不需要额外依赖） |
| 样式 | Tailwind CSS 4 | 深色画布 UI 快速成型 |
| 后端 | Node 24 + Express 5 + zod 4 | 代理 H3 接口、保管密钥、消除 CORS |
| 持久化 | **`node:sqlite`（Node 内置）** | 零原生依赖、零编译 |
| 构建 | pnpm workspace（web / server / shared） | 共享契约层，前后端规则永不漂移 |

**刻意不用**：无 LLM SDK、无 ComfyUI 工作流、无 `better-sqlite3` / `sharp` 等原生模块（图片处理走浏览器原生能力）、无状态管理以外的重型框架、无 multipart 依赖（素材直传原始二进制）。

**关键：开发期没有构建步骤**。Node 24 原生支持类型擦除，后端直接 `node src/bin.ts` 运行；前端由 Vite 直接消费 `packages/shared` 的 `.ts` 源码。为此全仓库遵守 `erasableSyntaxOnly`（不使用 enum、参数属性等不可擦除语法）。

> 环境注意：本机全局 npm 缓存在沙箱下不可写，因此 `.npmrc` 把 pnpm store 固定在仓库内的 `.pnpm-store`（与项目同盘，hardlink 生效）。首次安装若报 `ERR_PNPM_IGNORED_BUILDS`，已在 `pnpm-workspace.yaml` 里用 `allowBuilds.esbuild: true` 放行。

## 4. 接口契约（逐条对齐 docs/api）

**Base URL**：`https://api.minimax.cn`（设置项可切 `.com`）
**鉴权**：`Authorization: Bearer <API_KEY>`，**无 GroupId 参数**

| # | 方法 | 路径 | 用途 |
| :- | :--- | :--- | :--- |
| 1 | POST | `/v2/video_generation` | 创建视频生成任务 |
| 2 | GET | `/v2/query/video_generation/{task_id}` | 查询单任务 |
| 3 | GET | `/v2/query/video_generation` | 任务列表（分页 + 四种 filter） |
| 4 | DELETE | `/v2/video_generation/{task_id}` | 按状态取消或删除 |
| 5 | POST | `/v2/h3_context_ir` | 增强提示词（**不创建视频任务**） |
| 6 | POST | `/v2/video_regeneration` | 768P → 2K 再生成 |

### 4.1 关键约束台账

**状态机**：`queued | running | succeeded | failed | cancelled`
**删除/取消**：`queued → cancelled`（不扣费）；`succeeded|failed → deleted`；`running`、`cancelled` → **不可操作**。

**content 数组**：必含一项非空 `text`。元素 `type ∈ {text, image_url, video_url, audio_url}`，`role ∈ {first_frame, last_frame, reference_image, reference_video, reference_audio, base_video}`。
**互斥**：出现任一 `reference_*` 就不能出现 `first_frame`/`last_frame`，反之亦然。
**地址**：只接受公网 URL、`mm_file://{file_id}`、`data:<mime>;base64,<...>`。请求体总计 **≤ 64 MB**。

| | 文生/图生 | 多模态参考 | 分辨率 | 时长 |
| :--- | :--- | :--- | :--- | :--- |
| `MiniMax-H3` | ✅ | ✅ | `768P`、`2K` | 4–15 |
| `MiniMax-H3-Max` | ✅ | ❌ | `480P`、`768P` | 5–15（**无 4 秒**） |

**ratio**：t2va 必填且不能 `adaptive`；i2va 恒按 `adaptive`；r2va 可选默认 `adaptive`。

**素材限制**：图片 ≤30MB、256–5760px、比例 0.4–2.5，首帧 ≤1 / 尾帧 ≤1 / 参考图 ≤9；参考视频 MP4/MOV ≤50MB、≤3 段、单段与总计 ≤15s；参考音频 WAV/MP3 ≤15MB、≤3 段、总 ≤15s。`text` 上限：生成/Context-IR **7000** 字符，再生成 **40000** 字符。

**Context-IR 差异**：`model` 仅 H3；**无 `resolution` 字段**；产物在 `content.prompt`。
**再生成差异**：`source_task_id` 与 `content`(含 `base_video`) **必须且只能二选一**；`resolution` 仅 `2K`；`base_video` 恰好 1 个；必须原样重放全部输入且 `text` 用**最终 prompt**；源视频须符合 768P 规格（含音轨、24fps、宽高可被 32 整除、面积 768×768 ~ 768×1344、帧数 107–362）；`source_task_id` 模式**需白名单**。

**错误**：OpenAI 风格 `{type, error:{type,message,http_code}, request_id}`；HTTP 真实码 400/401/402/422/429/500；失败任务另有 `task.error:{code,message}`。产物为**限时链接**，任务仅保留 **7 天**。

### 4.2 计费口径（费用预估依据）

- 输出：H3 `768P` 0.50 / `2K` 0.80 元/秒；H3-Max `480P` 0.33 / `768P` 0.50 元/秒
- 输入素材：音频免费；图片 5 张内免费、超出 0.20 元/张；参考视频 0.80(2K)/0.50(768P) 元/秒
- 再生成：输出 0.30 元/秒；原任务素材重新计费（图片 0.15 元/张、视频 0.30 元/秒）
- Context-IR：输入 5.80、输出 23.00 元/百万 tokens

## 5. 节点模型

节点统一形状：`{ id, kind, position, params, runtime }`。`runtime`（任务状态、产物、错误、实际花费）只存在于前端内存，不写回图谱 JSON。

| 节点 | 输入端口 | 输出端口 | 主要参数 |
| :--- | :--- | :--- | :--- |
| `prompt` 提示词 | — | `text` | 长文本（7000 字符计数器） |
| `image` / `video` / `audio` | — | `media` | 本地上传 / URL；尺寸、时长、字节数 |
| `frameRole` 帧角色 | `media` | `media` | 首尾帧模式 / 参考图模式 |
| `videoGen` 视频生成 | `text`(必), `frames` | `video` | model / resolution / duration / ratio / 水印 |
| `contextIR` 上下文增强 | `text`(必), `frames` | `text` | duration / ratio |
| `regenerate` 再生成 | `video`, `text`, `frames` | `video` | 模式（按源视频 / 按任务 ID） |
| `taskStatus` 任务状态 | `any` | `video` | taskId（可跟随上游） |
| `taskList` 任务列表 | — | — | 类型筛选；本地 / 远端拉取 |

**数据流**：`text` 槽位接收字符串，上游 Context-IR 成功时注入增强提示词并保留 `rawText` 快照；`media` 槽位接收 `MediaRef`；`frames` 槽位携带 `role`，单张未指定角色时自动按 `first_frame` 处理。场景（t2va/i2va/r2va）由 content 组成自动判定，节点上实时显示徽标。

## 6. 执行引擎

- **「运行全图」**：对所有任务节点按**拓扑顺序推进式**执行。
- **「运行选中节点及其上游」**：只对目标节点创建任务，被依赖的上游节点**只求值、不重新提交**（避免点一个节点就把上游生成任务重跑一遍）。
- 运行前统一校验；任一被依赖节点有 error 就整体中止，绝不产生半成品。
- 付费动作默认弹窗确认（显示参数与预估金额），可勾选「本次会话内不再询问」。
- 每完成一步就把 `lastTaskId` / `lastPromptFinal` 写进节点参数，因此**刷新页面后能恢复**。
- 单分支失败不阻断其他分支；上游失败会跳过其下游并给出原因。

## 7. 持久化

SQLite 表：`projects` / `workflows` / `tasks` / `assets` / `skills` / `app_settings` / `runs`。

任务表同时保存 `request` / `response` / `prompt_raw` / `prompt_final` / `usage` / `content_url` / `local_path`，既支撑「再生成必须原样重放」的需求，也支撑产物过期后的本地回放。

**运行时恢复**：页面加载或切换工作流时，依据节点参数里的 `lastTaskId` 把任务状态、产物地址、Context-IR 增强提示词重新贴回节点。

## 10. 风险与缓解

| 风险 | 缓解 |
| :--- | :--- |
| 全局 npm 缓存不可写 | store 固定到仓库内 `.pnpm-store`；`allowBuilds` 放行 esbuild |
| 64MB 请求体上限 | 选文件时即按 `bytes×1.34` 预判，超限给出三条可执行建议 |
| 产物限时链接 + 7 天窗口 | 成功后自动转存并支持 Range 回放；失败时降级显示远端链接 |
| `source_task_id` 需白名单 | UI 明示；默认走 `base_video` 模式并自动回填原始素材与 `prompt_final` |
| Context-IR 提示词误用 | 任务表同时存 `prompt_raw` 与 `prompt_final`，再生成强制取最终版并标注来源 |
| 无真实 Key 无法验收 | 内置 `MOCK_H3` 模式回放完整契约（含真实 MP4 字节），`pnpm dev:mock` 一键启用 |
| 文件监听器被临时文件打崩 | Vite `server.watch.ignored` 显式忽略 `*.tmpdir` / `data` / `dist` |

## 11. 实现与计划的差异

实现过程中根据实测做了以下调整，均为对原方案的改进：

1. **新增服务端权威校验层**（`api-validation.ts`）。原计划只在前端校验，集成测试立刻暴露出「直接打接口可以绕过模型能力校验」的问题（H3-Max + 2K 竟然创建成功），因此把校验提升为服务端守门人。
2. **新增 MOCK 模式**。计划里只是可选项，实际成为端到端验收的关键手段 —— 没有它就无法在不花钱的前提下验证全链路。
3. **新增运行时恢复机制**（`engine/restore.ts`）。执行引擎跑在浏览器里，刷新即丢状态；改为每步落盘 `lastTaskId` 后可在刷新后重建。
4. **新增 `/api/assets/by-path`**。用于把本地转存路径还原成可回放的 URL。
5. **修复了两个真实缺陷**（由测试发现）：
   - 视频 / 音频节点没有在参数里记录自身 `kind`，导致它们被当成 `image_url` 送进接口（`node-params.ts` 的 `defaultParams` 已修正）。
   - 服务端在「未配置 API Key」时先报密钥错误，掩盖了真正的参数错误；改为校验优先。
6. **执行语义细化**：区分「运行全图」与「运行选中节点」，后者不重跑上游任务。
7. **界面按参考图 1–4 完整复刻**（见第 12 节）：极简节点、点击弹出的设置面板、
   生成方式与比例联动、底部创作台、左侧栏与底部工具栏对齐参考图。
8. **修复「一直提示已保存」**（用户反馈的真实 bug，见第 13 节）。

### 12.2 节点样式

改成参考图的极简风：默认近乎无边框（`rgba(58,69,87,.55)`），只有选中时才给一圈细描边；
标题是文件名 / 生成方式一行小字；参数不铺在卡片上，全部移到弹出的设置面板；
卡片宽度按内容区分（图片/视频 208px、视频生成 244px、提示词 260px）。

### 12.3 交互链路（参考图 2 → 3 → 4）

```
点视频节点      → 卡片下方弹出设置面板（底部创作台常驻）
点「全能参考」   → 比例给 7 项：自适应 / 16:9 / 4:3 / 1:1 / 3:4 / 9:16 / 21:9   （图3）
点「首尾帧」     → 比例只剩「自适应」                                          （图4）
```

关键设计：**比例的可选项直接来自 `PRESETS[].ratioOptions`**，与官方规则一一对应，
界面上不会出现「能点但接口会忽略」的假选项：

| 生成方式 | 场景 | 比例选项 | 说明 |
| :--- | :--- | :--- | :--- |
| 全能参考 | r2va | 7 项全给 | 多模态参考，ratio 可选 |
| 首尾帧 | i2va | 仅自适应 | 宽高比由输入图片决定，接口忽略其他值 |
| 首帧 | i2va | 仅自适应 | 同上 |
| 文生视频 | t2va | 6 项（无自适应） | 官方要求必须显式指定具体比例 |

切换生成方式时 `coerceRatio()` 会把当前比例收敛到合法值，不会留下会被静默忽略的参数。

### 12.4 设置面板（参考图 3 / 4）

五个分区与参考图一一对应：**生成方式**（分段控件）→ **比例**（图标卡片，带宽高比小方框）→
**清晰度**（768P / 2K 分段）→ **时长**（4s–15s 小块，超出模型范围的置灰）→ **有声视频**（有声 / 无声）。

额外补了三项参考图没有但必要的内容：模型切换（H3 / H3-Max，联动清理不支持的档位）、

### 12.5 关于「有声视频」

官方接口**没有**「是否配音」这个参数 —— 声音由提示词与参考音频决定。
因此这个开关落成一段**附加提示词**（`applySoundDirective()`，幂等、可反复切换），
并在面板上如实标注这一点，不假装它是一个接口参数。

## 13. 已修复的问题

### 13.1 「一直提示已保存」

**现象**：顶栏保存状态一直在「刚刚已保存」，而且真的在反复发 `PUT /api/workflows/:id`。

**根因链**：

1. 任务轮询每 4 秒把任务状态推回节点 → `restoreRuntimes()` → `setNodeRuntime()`；
2. 早期实现**无条件** `nodes.map(...)` 重建整个数组 → `nodes` 引用每次都变；
3. `AppShell` 的自动保存 `useEffect` 依赖 `[nodes, edges, ...]` 引用 →
   每次都被判为「有变化」→ 900ms 防抖**被反复重置**，而且每轮都真的发一次 `PUT`；
4. `save()` 里更新 `savedAt` → 顶栏一直显示「刚刚已保存」。

**修复**（三处，缺一不可）：

| 位置 | 改动 |
| :--- | :--- |
| `canvas/workflow-types.ts` | 新增 `runtimeEquals()` / `issueCountEquals()` 浅比较 |
| `store/graph.ts` | `setNodeRuntime` / `setIssues` / `setRun` 在内容未变时**不产生新对象**；新增 `graphSignature`（只含会被持久化的字段：id/kind/position/params/disabled/连线），由包了一层的 `set` 在任何图谱变更后自动重算；`save()` 增加「与上次落盘签名一致则直接返回」的去重 |
| `layout/AppShell.tsx` | 自动保存改依赖 `graphSignature` 而非 `nodes`/`edges` 引用；移除不再需要的 `skipFirst` |

**为什么用内容签名而不是深比较**：运行时状态（任务进度、产物地址、校验计数）每几秒都会被刷新，
它们本来就是内存态、不该触发落盘。把「会被持久化的字段」单独摘要出来，语义最清晰，也最快。

**回归防护**：新增 `store/graph.test.ts`（15 例）与 `store/save-dedup.test.ts`（2 例），
其中直接断言「重复写入相同运行时状态后 `nodes` 数组引用不变」「图谱签名不变」
「连续 8 次状态推送 + save 只发出 1 次 PUT」。

### 13.2 设置面板被底部创作台挡住

**现象**：点视频节点弹出设置面板后再点「全能参考」，面板下半部分被底部创作台盖住，看不到「比例」。

**根因**：设置面板原先渲染在**节点内部**，而节点属于 React Flow 的 `.react-flow__viewport`
（`z-index: 4`，本身就是一个层叠上下文）。创作台是画布容器的兄弟节点、`z-index: 20`，
所以无论面板自己写多高的 z-index，都不可能越过创作台。

**修复**：新增 `canvas/NodeFloatingPanel.tsx`，用 `createPortal` 把面板渲染到 `document.body`，
并用 `useStore` 订阅节点的绝对坐标与尺寸、配合 `useViewport()` 换算出屏幕位置：

- 水平贴住节点左边缘，但不超出视口
- **优先向下弹**；下方空间不足时自动**向上弹**（用 `ResizeObserver` 量真实高度来判断）
- 面板挂 `nowheel` + 拦截 pointerdown / click / wheel，避免在面板上操作时拖动或缩放画布

### 13.3 节点操作条「点不动」

**现象**：悬停节点出现的「▶ 运行 / ⧉ / ×」三个按钮点下去没反应。

**第一次修错了方向**：以为是 React Flow 的拖拽冲突，加了 `nodrag`。
这确实有必要（否则 `pointerdown` 会被判成拖拽起手），但**不是根因**，所以用户反馈「还是点不动」。

**真正根因**：操作条当时挂在节点**外面上方**（`absolute -top-8`）。
鼠标从节点向按钮移动时会先离开节点 → `onMouseLeave` 触发 → 操作条立刻
`opacity-0 pointer-events-none` → 按钮永远等不到 click。

**修复**：

| 改动 | 作用 |
| :--- | :--- |
| 容器加 `pt-8`，操作条改成 `top-1` 落在**内边距里** | 操作条成为悬停区的一部分，鼠标移过去不再触发 leave |
| 非悬停态只降透明度，**去掉 `pointer-events-none`** | 按钮任何时刻都可点，也不受过渡动画影响 |
| 保留 `nodrag nopan` + 拦截 `onPointerDown` | 顺带解决拖拽冲突 |
| CSS 里端口手柄 `top: calc(50% + 16px)` | 补偿顶部多出的 16px，手柄仍对齐内容区 |
| 内容包一层 `relative z-10` | 内容不会盖住操作条 |

### 13.4 设置面板无法移动

**修复**：`NodeFloatingPanel` 顶部加一条 34px 的透明抓手（`cursor-grab`），
按住即可把面板拖到任意位置。拖动量是**屏幕坐标增量**并叠加在节点锚点上 ——
所以拖动之后节点再移动，面板依然跟着走，只是保持用户设定的相对偏移。
切换节点时偏移自动清零，避免上一个节点的位置影响新节点。

### 13.5 底部工具栏的 ＋ 加的是「对话」而不是节点

**现象**：底部工具栏的 `＋` 直接新建了一个提示词节点，与参考图里「添加节点」的语义不符。

**修复**：新增 `layout/NodePickerMenu.tsx` + `canvas/canvas-bridge.ts`。
点 `＋` 弹出「添加节点」菜单：按输入 / 组织 / 任务 / 管理分组列出全部 10 种节点，
支持搜索（回车加第一个）、支持直接拖到画布，
点击则通过桥接把节点加到**画布可视区中心**（略微上移以避开创作台）。

桥接的作用：把 React Flow 实例的 `screenToFlowPosition` 与画布视口矩形暴露给菜单，
避免为了拿坐标而把菜单塞进 `ReactFlow` 子树里（那样会被节点层裁剪）。

**回归防护**：新增 `layout/NodePickerMenu.test.tsx`（7 例，含「点图片加的是图片节点而非提示词」
「节点落在可视区中心」「无画布实例时不报错」）与 `canvas/NodeShell.test.tsx`（6 例，
其中三条专门锁死操作条的结构：必须挂在容器内部、容器必须有 `pt-8`、
未悬停时不得出现 `pointer-events-none`）。

### 13.6 设置面板的关闭按钮点不动 + 面板太长

**问题一：右上角的 × 点不动**

上一轮为了支持拖动，我在面板顶部盖了一层 40px 高的透明抓手（`cursor-grab`）。
它把落在该区域的点击全吃掉了 —— 而 × 正好在那一行。

**修复**：抓手层加 `pointer-events: none`。
拖动本身不依赖它：由面板容器的 `onPointerDown` / `onPointerMove` / `onPointerUp` 驱动，
抓手只负责提供光标与「这里可以拖」的提示。
同时拖动起点会跳过 `button / input / select / textarea / a`，按在控件上不会误触发拖动。

**问题二：面板太长，一屏放不下**

原来所有分区垂直堆叠，一列排到底。

**修复**：改成**三列横向布局**，面板宽度从 300px 提到 760px（按视口自适应，
窄屏自动退化为单列）：

| 列 | 内容 |
| :--- | :--- |
| 1 | 生成方式（2×2 网格）· 模型 · 清晰度 |
| 2 | 比例（图标卡片，一行放得下 3 个） |
| 3 | 时长（一行 6 个）· 有声视频 |

底部单独一行放「本次请求摘要 + AIGC 水印 + 运行前确认 + 预估 + H3创作指南 + 生成」。

**回归防护**：新增 `canvas/NodeFloatingPanel.test.tsx`（4 例），

## 14. 一键启动

`启动.cmd`（Windows 双击）/ `node scripts/start.mjs`（跨平台）。

### 14.1 它做了什么

| 步骤 | 说明 |
| :--- | :--- |
| 环境检查 | Node 版本 ≥ 22（本项目用原生类型擦除跑 TS，低版本跑不起来）；pnpm 是否存在 |
| 依赖自愈 | `node_modules` 不存在就自动 `pnpm install`，fresh clone 直接双击也能跑 |
| 配置自愈 | 没有 `.env` 就从 `.env.example` 复制一份 |
| 端口探测 | 默认 8787 / 5173，被占用就自动往后找（最多 40 个） |
| 启动 | 同时拉起后端与前端，日志带 `[api]` / `[web]` 前缀 |
| 就绪确认 | 轮询后端 `/api/health`，通过后才算启动完成 |
| 打开浏览器 | 默认自动打开 WebUI |
| 干净退出 | Ctrl+C 时把两个子进程连同孙进程一起收掉，端口不残留 |

### 14.2 踩过的坑（都写进代码注释了）

**1）Vite 整站 404**
从仓库根启动时 Vite 用 `process.cwd()` 当根目录，于是去根目录找 `index.html`。
试过在配置里写 `root`，但 Vite 转译配置后路径解析不可靠；
也试过 CLI 的 `--root` —— **它不是选项，root 是位置参数**，直接报 `Unknown option`。
最终方案：**把 web 子进程的 `cwd` 设成 `apps/web`**，最直白可靠。

**2）只绑 IPv6 导致 127.0.0.1 连不上**
一旦从命令行传了 `--port`，Vite 就不再读配置文件里的 `host`，退回只绑 `::1`。
所以启动器必须同时显式传 `--host 127.0.0.1`。

**3）前端拿不到后端端口**
Vite 的代理目标写死在配置里，而端口是动态探测的。
改为配置文件读取 `H3_API_PORT` 环境变量，启动器把真实端口注入 web 子进程。

**4）Ctrl+C 留下孤儿进程**
最初用 `pnpm -C apps/server dev` 启动，多一层中间进程，
Windows 上 `child.kill()` 带不走孙进程，端口一直被占。
改为**直接用 `process.execPath` 跑入口文件**（`node --watch-path=… apps/server/src/bin.ts`、
`node node_modules/vite/bin/vite.js`），pid 就是真正的服务进程，
退出时用 `taskkill /T /F` 整棵树收掉。
顺带用 `--watch-path` 限定只监听服务端源码 —— 不加的话 `node --watch` 会盯着整个工作区，
`node_modules` 里任何写入都触发一次无意义重启。

**5）文件监听器被临时文件打崩（第三次遇到）**
编辑器/工具做「原子写」时会先写 `.foo.123.tmpdir/bar.tmp` 再改名。
之前写的 `**/*.tmpdir/**` 漏得掉它 —— 因为 **picomatch 默认不匹配点开头的名字**。
补上 `**/.*.tmpdir/**` 与 `**/.*.tmpdir`，并把 `data/`、`scripts/` 一并排除。

**6）pnpm 检测的连锁反应**
为了消掉往 `shell:true` 调用里传参数的 DEP0190 警告，改成 `spawnSync('pnpm.cmd', …)` ——
结果 Windows 上 Node 在 `shell:false` 下无法执行 `.cmd`，检测直接失败。
最终改为**直接查 PATH**（结合 `PATHEXT`），既准确又没有警告。

### 14.3 双击 `启动.cmd` 没反应

**现象**：双击后窗口一闪而过，什么都没发生。

**根因**：`.cmd` 文件是 **LF 换行**，而 `cmd.exe` 只认 **CRLF**。
实测 `cmd /c "启动.cmd --help"` 直接报
`The syntax of the command is incorrect.`，退出码 255。

被编辑器或非 Windows 环境写过的批处理文件很容易变成 LF，
而这个仓库其他文件统一是 LF —— 等于一直踩在雷上。

**修复**：

1. 三个 `.cmd` 全部转成 CRLF
2. 新增 `.gitattributes` 钉死 `*.cmd text eol=crlf`，避免以后被改回 LF
3. **`.cmd` 内容改成纯 ASCII** —— 顺带解决另一个隐患：
   `cmd.exe` 默认跑在 GBK 代码页（本机 936），UTF-8 的中文经 `echo` 出来是乱码。
   现在所有中文都由 Node 输出（Node 往控制台写 UTF-8 是正常的），
   `.cmd` 只负责环境检查与转发。

### 14.4 停止与清理

- 正常：启动窗口按 `Ctrl+C`
- 窗口被强行关闭后：双击 `停止.cmd`（即 `node scripts/start.mjs --stop`），
  它会读 `data/dev-runtime.json` 记录的端口，把占用这些端口的进程收掉
- 启动器会把端口记在 `data/dev-runtime.json`，下次启动优先复用（端口稳定，书签不会失效）

### 14.5 回归防护

`scripts/start.test.mjs`（17 例）会**真的把服务拉起来**再验证：

- `--help` 输出完整用法；`--stop` 在无运行时记录时不崩
- 前端与后端都监听在 `127.0.0.1`（不是只绑 IPv6）
- 首页返回的是真正的应用（含 `<div id="root">` 与 `/src/main.tsx`），不是 404
- 前端代理确实把 `/api` 转给了后端
- 运行时文件记录了真实端口
- **收掉启动器后端口被释放，不留孤儿进程**
- **三个 `.cmd` 逐个检查：CRLF 换行、纯 ASCII、以 `@echo off` 开头并调用启动器**

测试用高位端口（55173 / 55187），不会和用户开着的 5173 / 8787 打架。

## 15. 已知边界
- 再生成的「按任务 ID」模式需 MiniMax 侧开通白名单（接口硬要求）
- 仅支持查询最近 7 天的任务，超出窗口只能看本地缓存
- `running` / `cancelled` 状态不可取消或删除（接口硬限制，界面已禁用并说明原因）
- v1 不暴露 `callback_url`（本地不可达），不做 H3 之外的 MiniMax 能力
- 服务默认只监听 `127.0.0.1`，无多用户与鉴权体系
- 参考图里的「ComfyUI 工作流 Beta」按需求未实现（该项目不接受 ComfyUI 工作流）
- 参考图右下角的 `✳ 560` 是平台侧额度口径；本项目按官方「按量计费」文档显示**人民币预估**，
  任务成功后依据 `usage` 折算实际花费
